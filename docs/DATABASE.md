# SQLite и переход на PostgreSQL

Локальный запуск: `npm run local`. Отдельный сервер БД не нужен; Node.js 24 использует встроенный `node:sqlite`. Первая загрузка создаёт `data/code-climb.sqlite` и применяет `server/migrations/*.sql`. Не храните рабочую БД на синхронизируемой сетевой папке при нескольких одновременных машинах. Для этого проекта в OneDrive можно перенести БД вне OneDrive через `SQLITE_PATH`.

Настройки процесса: `DB_DRIVER=sqlite`, `SQLITE_PATH=<абсолютный путь>`. По умолчанию путь относительно корня проекта. База содержит пользователей, хеши паролей, хеши сессий, раздельный прогресс Python/C++, версии схемы и лимиты входа.

Сделать согласованную резервную копию при работающем сервере: `npm run db:backup`. Копия появляется в `data/backups/`. Не копируйте только `.sqlite` вручную при открытом WAL. Для восстановления остановите приложение и сохраните старую БД вместе с `-wal`/`-shm` отдельно, затем восстановите согласованную копию. Никогда не публикуйте БД и резервные копии.

## Контракт хранилища

HTTP-обработчики используют только `server/repository.mjs`, а SQLite SQL содержится только в `server/sqlite-repository.mjs`.

Асинхронные методы: `findUser`, `findEmail`, `createUser`, `bootstrapAdmin`, `createPending`, `getPending`, `deletePending`, `rotateCode`, `verifyRegistration`, `createSession`, `getSession`, `deleteSession`, `cleanup`, `rateLimit`, `getProgress`, `saveProgress`, `adminOverview`, `adminUsers`, `adminProgress`, `adminAction`, `close`. `createUser` используется для прежних аккаунтов/тестов; публичная регистрация проходит через одноразовый код.

`saveProgress` атомарно сравнивает revision и возвращает новую либо null при конфликте. Классический маршрут хранится в `progress`, отдельные сложности — `course_progress`, все 15 уровней — `full_progress`. Старые записи не перезаписываются.

`verifyRegistration` атомарно проверяет HMAC/срок/лимит, увеличивает счётчик ошибочных попыток либо создаёт игрока и удаляет ожидающую регистрацию. `rotateCode` использует compare-and-swap предыдущего хеша. `rateLimit` атомарно увеличивает счётчик. Блокировка и отзыв сессий пишут `admin_audit` в той же транзакции; смена хеша администратора отзывает его сессии. Эти гарантии должны сохраняться в PostgreSQL.

## Перенос

1. Добавить `server/postgres-repository.mjs` с тем же контрактом, пулом соединений, параметрами `$1…` и атомарными транзакциями. Подключить его в `createRepository` для `DB_DRIVER=postgres`; сейчас неизвестный драйвер специально вызывает ошибку, а не молча использует SQLite.
2. Создать отдельные PostgreSQL-миграции с теми же логическими таблицами и ограничениями. IDs уже UUID-строки, состояния прогресса — JSON, хеши паролей переносимы. SQLite PRAGMA в PostgreSQL не переносить.
3. Остановить записи, сделать backup, перенести пользователей и прогресс, проверить количество записей и FK. Сессии при переходе безопаснее аннулировать, попросив войти заново.
4. Прогнать `tests/accounts.test.mjs` на новом адаптере, особенно конкурентные revision, уникальность логинов, rate limit и разделение пользователей.
5. Только после проверки переключить `DB_DRIVER` и конфигурацию соединения. Не удалять старую БД до проверки восстановления/отката.

PostgreSQL пока не подключён: выделен и протестирован интерфейс для миграции, а не заявлена готовая поддержка второго драйвера.
