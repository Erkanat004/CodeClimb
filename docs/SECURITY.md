# Границы безопасности CODE CLIMB

Эта версия разделяет тренировку и соревнование. Тренировка остаётся браузерной песочницей и не является защищённым рейтингом. Режим соревнования `/compete` использует отдельный серверный judge со скрытыми тестами и без клиентского fallback. Подготовлены локальный режим и конфигурация публичного HTTPS-запуска; реальную инфраструктуру нужно проверить перед публикацией. Абсолютной защиты от ошибок браузера, контейнера, зависимостей и ОС не существует.

## Исполнение решений

- В тренировке сервер аккаунтов **не компилирует и не исполняет** решения. C++ компилируется Clang 22 в WebAssembly; Python запускается CPython/Pyodide.
- Каждый запуск создаёт скрытый `iframe sandbox="allow-scripts"` без `allow-same-origin`, а внутри него — одноразовый Worker. Доступа к DOM приложения, его cookie, localStorage и SQLite у программы нет. Worker не получает файловых дескрипторов компьютера.
- CSP песочницы запрещает сеть (`connect-src 'none'`), внешние скрипты, картинки, формы и объекты. Разрешены только локальные blob-скрипты и eval для WASM-окружения. Код игрока передаётся structured clone, не вставляется в HTML. Родитель не исполняет команды из результатов и не делает сетевые запросы по указанию Worker.
- Среды загружаются приложением из фиксированного списка ресурсов и проверяются SHA-256. Это защита от повреждения/несовместимости ассетов, не от компрометации самого сервера, который выдаёт и код, и манифест.
- Файловые операции работают только в одноразовой виртуальной памяти. Удаление виртуального файла не удаляет файл компьютера. Нет нативного shell, процессов ОС, npm/pip-install или доступа к SQLite из решения.
- Максимум 30 000 символов решения; 120 секунд на загрузку, 30 секунд на компиляцию C++, 3 секунды на выполнение набора тестов. STOP уничтожает Worker. Повторные сообщения не продлевают таймер.
- C++: максимум 256 МиБ линейной памяти выполняемого WASM. Python: максимум 512 МиБ линейной памяти, включая интерпретатор. Эти значения **не являются лимитом всей памяти вкладки**: компилятор, JS-объекты и браузер используют дополнительную память. Браузер может завершить вкладку при нехватке ресурсов. Для жёсткого общего лимита требуется серверная VM/контейнер.
- Вывод ограничен, результаты проверяются по структуре и отображаются как текст, не HTML. C++ не получает произвольные JS imports; WASI работает только с виртуальной файловой системой.

## Соревнование и judge

- Дуэль доступна только авторизованным игрокам и только при здоровом `JUDGE_URL`. Если judge недоступен, сервер не создаёт комнату и не принимает решения.
- Оба игрока получают один язык, один набор из 5 задач и общий старт. Клиент не отправляет пройденный уровень как истину: сервер сверяет текущий уровень по БД, создаёт pending submission и продвигает игрока только после ответа judge.
- Исходный код соперника не возвращается API. В БД хранится хеш отправленного кода, статус и вердикт, но не полный текст решения.
- Обычная вставка и drag/drop отключены в редакторе дуэли. Это барьер против копирования, а не криптографическое доказательство авторства: владелец компьютера может использовать DevTools, макросы или перепечатать чужой код вручную.
- Judge рассчитан на отдельный Linux-хост или приватный сервис. Runner требует Docker, `runsc`, immutable image digest, `--network none`, `--cap-drop ALL`, `--read-only`, лимиты CPU/RAM/pids/files и одноразовый `/tmp`. Основной API не получает Docker socket.
- Python/C++ в judge выполняются в одноразовом контейнере с фиксированным harness. Скрытые тесты генерируются на сервере из `JUDGE_CASE_SECRET`; ожидаемые ответы не отправляются клиенту.
- Это всё равно требует эксплуатационной защиты: приватная сеть, firewall, обновления Docker/gVisor, лимиты на уровне хоста, мониторинг и отдельная проверка перед публичными призами или рейтингом.

## Реклама и подсказки

- Короткая подсказка в тренировке бесплатна. Подробная подсказка выдаётся сервером после подтверждённой рекламы, максимум 3 на раунд из 5 задач.
- Клиент не может сам открыть подсказку: он создаёт pending attempt, а unlock появляется только после серверного provider callback. Для AppLixir проверяется `gameApiKey`, `gameId`, `tid`, `userId` и MD5-подпись с `APPLIXIR_WEBHOOK_SECRET`.
- `ads.txt` отдаётся как обычный текст по `/ads.txt` через API/Caddy. Тестовый режим наград разрешён только локальному администратору и не должен использоваться публично.

## Аккаунты

- Локально сервер слушает только 127.0.0.1, origin фиксирован на http://localhost:5173. В production API находится во внутренней сети контейнеров; наружу выходит только Caddy с HTTPS. Данные — приватная SQLite, не `public/`, исключены из Git и образа веб-части.
- Веб-сервер запрещает отдачу `data/`, исходников локального API, `.sqlite` и WAL/SHM-файлов, в том числе через `/@fs/`. Папка `data/` с резервными копиями не входит в сборку веб-части.
- Пароли: scrypt (N=32768, r=8, p=3), случайная соль, сравнение constant-time. Параметры соответствуют одному из [вариантов OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Пароли и токены не логируются.
- Случайные 256-битные сессии на 7 дней; в БД только SHA-256 токена. Cookie HttpOnly, SameSite=Strict, узкий Path, обязательный Secure в публичном режиме. Secure отсутствует только для HTTP loopback.
- Изменения требуют точного Origin и специального заголовка; CORS не включён. API дополнительно проверяет Host и Sec-Fetch-Site. SQL использует параметры, доступ к прогрессу определяется серверной сессией, не переданным клиентом user_id.
- Лимиты входа сохраняются в SQLite; количество параллельных хеширований ограничено. Проверка длины запросов, паролей, черновиков и прогресса. Обновления прогресса используют revision, чтобы вкладки не перезаписывали данные молча.
- Новая регистрация: случайный шестизначный код, 10 минут, 5 попыток, ограничения IP/email и повторной отправки. В БД HMAC кода с серверным секретом. Проверка и создание аккаунта атомарны, код одноразовый. Пароль до подтверждения также хранится только хешем. Коды не возвращаются API и не пишутся в логи; локальный file-режим сохраняет тестовое письмо в приватной папке.
- Поле role задаёт сервер, клиент не может зарегистрироваться администратором. Все admin API проверяют роль. Блокировка и отзыв сессий действуют сразу, действия попадают в admin_audit. Смена серверного хеша администратора завершает его старые сессии.
- Публичный API проверяет точный Host, HTTPS origin и секретный заголовок доверенного proxy; адрес для лимитов берётся из перезаписываемого Caddy заголовка. Нельзя открывать порт API наружу, оставлять старый пароль администратора или добавлять другой proxy без адаптации настроек.

## Что не является защищённым

Тренировочные тесты и судья находятся в браузере. Владелец браузера может подделать свой тренировочный прогресс через DevTools/API. SQLite хранит прогресс, но не делает его доказательством честного прохождения. Для общего рейтинга используй только `/compete` с подключённым judge; перед публичными наградами всё равно нужен независимый аудит и проверка инфраструктуры.

Не выставляйте dev-сервер в публичную сеть через `--host 0.0.0.0`. Для сети используйте [инструкцию развёртывания](DEPLOYMENT.md). Нужны проверка DNS/TLS и доставки почты, резервное копирование с проверкой восстановления, обновления и мониторинг. Самостоятельное восстановление пароля игрока и MFA пока не реализованы. Лимиты приложения не заменяют защиту от DDoS у хостера. Успешные тесты не заменяют независимый аудит.

Базовые браузерные механизмы: [sandbox iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), [CSP и Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers).
